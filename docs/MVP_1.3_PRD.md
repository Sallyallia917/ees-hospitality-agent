# EES Hospitality Agent — MVP 1.3 PRD

- 版本：MVP 1.3
- 产品主题：受控的个人订单只读查询
- 状态：设计基线（待评审）
- 数据性质：全部订单、住客身份与认证凭据均为合成演示数据
- 依赖基线：MVP 1.2（混合意图分类、确定性路由、多轮上下文）

## 1. 背景与问题

MVP 1.2 已能识别公共知识咨询、个人订单咨询、实时库存、交易请求、服务请求、投诉与安全事件，并按业务依赖路由。但个人订单类问题只能提示用户转人工，系统尚不能在完成身份与订单归属校验后返回订单事实。

住客常见问题包括“我订的是什么房型”“订单含早餐吗”“我哪天入住”。这些问题不能由公共 FAQ 推断，必须读取与当前住客身份绑定的订单记录。

## 2. 产品目标

在不接入真实 PMS/OTA 的前提下，构建一个可验证的受控查询闭环：
1. 明确识别个人订单查询意图。
2. 通过演示认证流程建立一个可验证的演示身份。
3. 对每次查询执行订单归属授权校验（认证成功不等于任意订单可读）。
4. 仅通过只读订单工具读取允许披露的字段。
5. 对无身份、无匹配订单、多订单、越权、数据缺失和工具异常给出安全且可解释的结果。
6. 保留审计信息，避免模型直接访问数据库或编造订单事实。

## 3. 非目标

- 不接真实 PMS、OTA、支付、短信、微信或身份服务。
- 不执行取消、退款、改期、换房、续住等交易操作。
- 不查询实时房态、停车位或其他实时库存。
- 不创建真实工单、不发送真实消息。
- 不将模拟认证描述为生产级身份认证。
- 不引入多 Agent、微服务或复杂工作流平台。

## 4. 用户与核心场景

主要用户：使用演示门店服务的住客。

| 场景 | 输入示例 | 预期行为 |
|---|---|---|
| 未认证查询 | 我预订的是什么房型？ | 说明需先完成身份验证，不返回订单数据 |
| 认证后单订单查询 | 我订单含早餐吗？ | 认证通过后仅查询本人订单字段 |
| 多订单 | 我有两个订单，查哪个？ | 默认展示最近三笔本人可访问订单；用户描述了日期、房型或房源时，先按描述筛选，再展示匹配摘要供选择 |
| 越权查询 | 帮我查朋友的订单 | 拒绝访问，不泄露订单是否存在 |
| 不存在订单 | 查订单 DEMO-999 | 返回统一的无权访问/未找到提示，不暴露其他用户数据 |
| 订单字段缺失 | 早餐权益是什么？ | 明确标注数据未维护，转人工核实，不猜测 |
| 交易请求 | 帮我把大床房换成双床房 | 沿用 MVP 1.2 交易转人工，不调用只读查询冒充完成 |
| 公共政策 | 酒店允许换房型吗？ | 沿用 RAG 公共知识链路 |
| 安全事件 | 房间有煤气味 | 安全响应最高优先级，不受认证流程阻塞 |

## 5. 用户流程

1. 用户提出个人订单问题。
2. MVP 1.2 分类器识别为 booking_related_inquiry。
3. 确定性路由判断需要订单数据及认证身份。
4. 若未认证，提示进入演示身份验证；认证成功后建立 session 中的 verified principal。
5. 若本人存在一笔订单，进入字段白名单只读查询。
6. 若本人有多笔订单，默认按最近更新时间/入住日期排序展示最近三笔可访问订单；若用户描述了入住日期、房型、房源或订单状态，则先用确定性条件过滤，展示匹配结果供选择。若匹配结果仍超过三笔，分页/提示缩小范围，不倾倒全部订单。
7. 查询工具先校验 principal 与 booking.customer_id 的归属关系，再返回允许字段。
8. 应用层验证工具结果结构与字段完整性，再组织自然语言答复。
9. 记录审计事件：请求 ID、演示用户 ID、订单 ID（内部标识）、查询字段、结果状态、时间；不得记录明文认证凭据。

## 6. 演示身份验证方案

采用显式标注的 demo-only 验证适配器，不模拟真实短信 OTP，不将用户自述或任意输入的 VERIFIED 状态当作认证。

建议演示流程：用户从固定演示账号中选择身份，并输入该演示账号对应的预置验证码；服务端适配器校验后返回内部 principal。演示凭据仅用于本地/公开作品集体验，必须在 README 标注为公开测试凭据，不得复用真实个人信息或真实密码。

安全约束：
- 身份状态由认证适配器产生，不由聊天文本、LLM 或前端自由输入决定。
- session 中保存 principal 标识和认证状态；不能仅凭用户输入 booking_id 即授权。
- 每次订单查询仍独立校验订单归属。
- 生产环境必须替换为可信身份提供方、短时令牌、速率限制、会话过期、重放防护及安全审计。本 MVP 不宣称满足生产认证标准。

## 7. 订单、取消规则与房源数据范围

模拟数据建议拆分为可关联的实体：
- customer：customer_id、display_name、masked_phone（仅演示显示，不作为授权依据）。
- booking：booking_id、customer_id、property_id、booking_status、room_type、check_in、check_out、guest_count、breakfast_entitlement、parking_entitlement、source_channel、cancellation_policy_id 或 booking_policy_snapshot。
- property：property_id、property_name、property_type、location、facilities、check_in_instructions、service_policy_refs、status。后续可扩展房源图片、房型、设施、交通、周边信息等，不要求 MVP 1.3 一次性实现所有字段。
- cancellation_policy：policy_id、version、timezone、effective_from、effective_to、windows。每个 window 定义截止时间/相对入住时间、费用类型、费用比例或固定金额、适用条件及说明。
- 数据必须使用虚构身份、虚构联系方式和演示房源；不使用真实住客数据。

取消规则必须明确时间基准和时区。例如：入住前 7 天（含）免费取消；入住前 3 至 7 天取消收取订单金额 30%；入住前 3 天内不可取消。以上仅为演示规则，不代表真实酒店政策。规则区间必须无重叠、无空档，边界包含关系要明示；订单应关联下单时适用的规则版本/快照，避免后续政策修改导致历史订单展示口径漂移。

MVP 1.3 允许展示订单关联的取消/退款规则和逐条时间窗口；可在数据完整时展示规则对应的费用说明或静态示例。当前版本不计算真实退款金额、不判断支付渠道实际退款到账，也不执行取消/退款。若未来增加费用估算，必须基于订单金额、币种、规则版本、时区和边界测试，并明确标注“估算”。

允许返回字段：订单摘要、房型、入住/退房日期、入住人数、早餐/停车权益、订单状态、预订渠道、订单适用的取消规则、关联房源的已维护信息（仅在权限和数据范围允许时）。

禁止返回字段：完整手机号、证件号、支付凭据、内部风控标记、其他客户订单、未配置字段的推断值。

## 8. 功能需求与优先级

### P0
- FR-01：个人订单问题进入订单查询流程，不进入公共 FAQ RAG。
- FR-02：未认证状态不得读取订单。
- FR-03：认证适配器返回 principal，前端和 LLM 不得自行声明认证成功。
- FR-04：订单查询工具必须验证 booking.customer_id == principal.customer_id。
- FR-05：查询工具只读，字段白名单控制返回内容。
- FR-06：多订单时先列出当前 principal 可访问的订单摘要并要求选择。
- FR-07：订单不存在、无权限、数据缺失、工具异常均有安全兜底。
- FR-08：交易请求、实时库存、安全事件继续遵守 MVP 1.2 既有优先级与边界。
- FR-09：记录结构化审计事件，不记录明文凭据。
- FR-10：LLM 不得直接访问数据存储、不负责认证、授权或工具执行。
- FR-14：订单详情可读取订单关联的取消/退款规则版本，展示明确的时间窗口、费用类型、比例/金额和适用条件；规则缺失时明确提示未维护。
- FR-15：订单可关联独立 property 实体；房源信息采用可扩展字段/关联结构，避免把房源详情硬编码进订单。
- FR-16：取消规则仅作只读展示；不执行取消/退款，不声称已计算实际退款或完成退款。

### P1
- FR-11：界面显示当前演示认证状态和重置会话入口。
- FR-12：答复中说明数据来自演示订单库，并可查看脱敏订单摘要。
- FR-13：将认证、授权、工具查询和答复验证状态分别展示，便于调试与面试演示。

## 9. 异常与安全处理

| 条件 | 系统行为 | 禁止行为 |
|---|---|---|
| 未认证 | 请求认证 | 不查询订单 |
| principal 缺失/过期 | 重新认证 | 不沿用旧 VERIFIED 标志 |
| 订单不属于本人 | 拒绝访问 | 不透露订单是否属于他人 |
| 多订单未选择 | 按用户描述筛选；无描述时展示最近三笔摘要并请求选择 | 不展示全部订单、不擅自选择 |
| 订单不存在 | 统一提示无法找到可访问订单 | 不泄露其他客户订单存在性 |
| 字段为空/取消规则缺失 | 标注未维护并转人工 | 不让 LLM 补全或套用其他订单规则 |
| 取消规则时间边界不明确 | 不展示推断结论，提示人工核实 | 不猜测截止时间或费用比例 |
| 存储/工具异常 | 安全失败、提示稍后重试或人工核实 | 不返回缓存猜测结果 |
| 交易请求 | 转人工 | 不通过只读工具执行变更 |
| 安全事件 | 立即安全指引 | 不等待认证 |

## 10. 验收标准

- AC-01：未认证用户查询房型时不返回任何订单字段。
- AC-02：认证用户查询本人唯一订单时，返回字段与数据库记录完全一致。
- AC-03：多订单时默认仅展示最近三笔本人订单；描述筛选可返回匹配订单，用户明确选择后再查详情。
- AC-04：用户不能通过修改输入中的订单号访问他人订单。
- AC-05：未配置字段不由模型猜测。
- AC-06：工具异常时不输出成功结果或虚构订单内容。
- AC-07：房型变更、退款等交易请求仍只转人工。
- AC-08：安全事件优先级高于认证与订单查询。
- AC-09：审计日志不含明文验证凭据和不必要的个人信息。
- AC-10：所有自动化测试通过；线上演示场景由用户实际验收。合成测试通过不等于生产准确率。
- AC-11：取消规则按订单关联的规则版本展示，时间窗口、时区、费用和边界条件可追溯；不完整规则不输出确定性结论。
- AC-12：房源信息通过 property_id 关联独立房源实体；新增房源属性不破坏订单查询契约。
- AC-13：订单列表默认最多展示最近三笔；按用户描述过滤时只展示符合条件且本人有权访问的结果。

## 11. 评测计划

建立独立 MVP 1.3 合成评测集，至少覆盖：
- 未认证访问（含提示注入/自称已认证）
- 正常本人单订单查询
- 多订单澄清与选择
- 他人订单越权
- 伪造/不存在订单号
- 字段缺失与空值
- 工具异常与超时
- 交易请求隔离
- 公共 FAQ 与个人订单问题区分
- 多轮对话中身份状态保持与重置
- 安全事件优先级

关键指标分开报告：意图识别匹配率、认证门槛拦截率、订单归属授权正确率、字段准确率、异常安全失败率、禁止动作发生次数。安全类硬门槛必须为零违规；不能用总体平均分掩盖越权失败。

## 12. 证据边界与发布说明

订单和身份数据全部为合成数据。演示认证只验证产品流程和权限架构，不构成真实身份安全方案。自动化测试仅证明已覆盖案例中的行为；真实业务准确率、人工节省、满意度、收入提升均未测量。对外展示必须清楚标注模拟数据和非生产认证。
